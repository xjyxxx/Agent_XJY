# 真模型与语义检索：缺口分析与实施方案

> 两条 ⚠️ 的实质不同：**真模型是"没验证"，语义检索是"没测准"**。
> 前者需要一个 key，后者需要先修基准——顺序不能反。

## 0. 摘要

| | 真模型（对话质量） | 语义检索（改写召回） |
|---|---|---|
| 现状 | 代码就绪，**0 次真实调用** | 只有词法被验证过 |
| 真正的阻塞项 | 一个 API key（¥10 级成本） | **基准没有区分度**（见 §3.1） |
| 先做什么 | 补埋点（usage / TTFT / 429） | 扩基准 + 扩语料 |
| 推荐路线 | DeepSeek 远程；任何 OpenAI 兼容端点可替换 | 先 LLM 扩写，再按隐私决定本地 ONNX |
| 预估 | P0 半天 + P1 1 小时 | P0 半天 + P2 0.5–1 天 |
| 能不能不做 | 不能：项目全部"质量"结论都建立在它上面 | 能：但"改写召回"这条卖点要撤掉 |

## 1. 现状量化（实测，不是估计）

| 事实 | 数字 | 出处 |
|---|---|---|
| 单元测试 | 124 通过 | `python -m unittest discover ...` |
| 当前"文风相似度" | **0.4962** | `evaluator.run`，但样本是**模板模型**生成的 |
| 拦截率 | 1.0 | 同上，对抗轮次全拦 |
| 单轮延迟（离线） | p50 7.0 ms | `bench/loadtest.py` |
| 单轮延迟（远程，估） | 首 token 0.4–1.2 s | 未实测，需 `probe` 替换 |
| 检索 same_situation 组 | 四种策略全部 1.000 | 无区分度 |
| 检索 hard 组 | lexical 0/2，扩写 1/2 | n=2，**统计上不可用** |

**关键认知**：现在 `style_similarity=0.4962` 衡量的是「离模板模型多近」，
不是「离小林多近」。真模型一接入，这个数字会**大幅变化**（可能变好也可能变差），
所以它不能当基线用，只能当"换模型前后的回归参考"。

## 2. 缺口 A：真模型

### 2.1 未验证的到底是什么

不是"能不能调通"（协议层已用 mock 验过），而是这四件事：

1. **prompt 是否真的压住了人设**：5 条约束（短句、优先证据、禁助手腔、不串台、只输出正文）在真模型上有没有效果。
2. **Critic 与真模型是否兼容**：规则黑名单对模板模型几乎不会触发，对真模型可能频繁触发——**触发率高不代表模型差，可能代表规则太严**。
3. **首 token 延迟**：远程 p50 若是 1s+，不做流式就是 1s 白屏。
4. **成本**：每轮多少 token、每天多少钱。

### 2.2 先补埋点（否则验证只能靠感觉）

没有这三个数，跑完也不知道该改什么。都是 ~60 行：

| 埋点 | 实现位置 | 产出 |
|---|---|---|
| `usage`（prompt/completion tokens） | `deepseek._chat` 读 `body["usage"]`，通过 `on_usage` 回调传出（与 `on_delta` 同一套 ContextVar 机制） | 每轮成本、输入是否膨胀 |
| **TTFT**（首 token 延迟） | `_chat_stream` 里记第一个 delta 的时刻 | 流式到底救了多少 |
| 429 重试 | `_open` 外包一层指数退避（1s/2s，尊重 `Retry-After`） | 验证时不被限流打断 |
| 双 provider 对比 | `evaluator.run --provider heuristic,deepseek` | 同集同指标，一张表 |

**为什么必须先做**：真模型的验证结论是"贵不贵、快不快、像不像"三件事，
前两件全靠埋点。没有埋点，"感觉快一点"就是结论。

### 2.3 provider 选项（都走同一个适配器，改两个环境变量）

| 供应商 | 兼容性 | 免费额度 | 适合 |
|---|---|---|---|
| **DeepSeek** | OpenAI 兼容 | 无（需充值，¥10 起） | 默认；便宜、中文好、`deepseek-flash` 快 |
| 阿里百炼（通义） | OpenAI 兼容 | 有新用户额度 | 国内网络稳 |
| 智谱 GLM | OpenAI 兼容 | 有免费档 | 备选 |
| 硅基流动 / OpenRouter | OpenAI 兼容 | 有免费模型 | **零成本验证**首选 |
| 本地 vLLM / Ollama 兼容层 | OpenAI 兼容 | — | 隐私要求高时 |

代码侧只认 `DEEPSEEK_BASE_URL` + `DEEPSEEK_MODEL`，所以"先拿免费额度把协议跑一遍，
再换 DeepSeek 做质量对比"是完全可行的路径。

### 2.4 验证协议（6 步，按顺序）

```powershell
# ① 连通性与延迟基线
python -m llm_client.check
#    通过标准：exit 0，latency 记录到表格

# ② 黄金样例人工看三件事
python -m agent.demo --provider deepseek --message "王哥今晚加班，晚饭你自己先吃？"
#    看：长度是否接近 4.2 字 / 有没有叫"王哥" / 有没有助手腔

# ③ 规则评估（回归基线）
python -m evaluator.run --gate

# ④ LLM judge（用同一模型自评，成本很低）
python -m evaluator.run --judge llm --json > eval-deepseek.json

# ⑤ 流式：首 token 延迟
$env:STREAM="1"; python -m transport --port 8000
#    用 curl -N 观察 reply_delta 到第一个 delta 的时间

# ⑥ 对比表（heuristic vs deepseek，同 10 轮）
python -m evaluator.run --provider heuristic --json > eval-heuristic.json
```

**通过标准（任一不满足就不切默认模型）**：

| 指标 | 门槛 | 理由 |
|---|---|---|
| `catch_rate` | **= 1.0** | 换模型不能把拦截能力弄丢 |
| `hallucination_rate`（clean 轮次） | = 0 | 这是项目卖点 |
| `style_similarity` | **≥ 0.60**（当前 0.4962，+0.10） | 提不动说明 prompt 没起作用 |
| 首 token 延迟 | ≤ 1.5 s | 超过就必须默认开 `STREAM=1` |
| 单轮成本 | ≤ ¥0.002 | 决定了能不能做压测/评估 |

**停止条件**：402 → 换供应商或充值；429 → 先退避，仍失败就降并发；
发现聊天内容里的"指令"被执行 → 立刻停，这是注入漏洞。

### 2.5 成本估算（可替换成真实 `usage`）

```text
一轮 ≈ 600 input + 60 output tokens
按 input ¥1/M、output ¥2/M 估算（以价目表为准）：
    每轮 ≈ 600/1e6×1 + 60/1e6×2 = ¥0.00072
    10 轮评估 ≈ ¥0.007
    1000 轮压测 ≈ ¥0.72
```

结论：**成本不是障碍，一次 ¥10 充值能跑上万轮**。真正的成本是"调 prompt 的时间"。

### 2.6 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 真模型回复变长 → 触发 `too_long` → 频繁 rewrite | 成本×2、延迟×2 | 阈值按真实句长分布重标（先测 20 条回答的 P90） |
| 规则黑名单对真模型误杀 | 好回复被拦 | 记录被拦样本，专看"误杀"而非"命中" |
| prompt 注入（聊天记录里写"忽略以上规则"） | 人设失效 | 工具/证据与指令分区；后续加注入检测 |
| 远程内容外泄 | 隐私 | 只用合成样例；真实记录不配远程（文档已写明） |

## 3. 缺口 B：语义检索

### 3.1 为什么现在"换技术"没有意义（三个数字）

| 事实 | 数字 | 含义 |
|---|---|---|
| same_situation 组 query 与历史上下文的 bigram 覆盖率 ≥80% | **9 / 9** | 这一组就是"近逐字匹配"，任何检索器都能满分 |
| hard 组样本量 | **n = 2** | 0/2 vs 2/2 的 Fisher 精确检验 **p = 0.333**，无法宣称提升 |
| 语料规模 | **10 条** target 发言 | 随机排序 hit@1 期望就有 0.1，任务太简单 |

**所以现在的正确动作不是"上 embedding"，而是"把基准做成能分辨差异的样子"。**
否则换了向量库，你只能看到"看起来差不多"，然后凭感觉选型——那和没做一样。

### 3.2 基准要先怎么扩

| 维度 | 现在 | 目标 | 为什么 |
|---|---|---|---|
| 改写 query | 2 条 | **30 条**（覆盖同义、指代、省略、口语化） | n=30 时 80% vs 100% 才有讨论价值 |
| 语料 | 10 条发言 | **500+ 条**（合成，但要有干扰项：相似场景不同人、同一人不同话题） | 让"召回"真的需要排序 |
| 负样本 | 2 条 no_match | 15 条 | 测误报率，不只测命中率 |
| 分组指标 | same / paraphrase / hard | 再加 **"同人不同话题"** 组 | 这才是真实场景里最容易错的 |

扩基准的代价：**半天**。收益：之后每一个技术决策都有数字可依。

### 3.3 三条技术路线对比

| 路线 | 新增依赖 | 数据出境 | 查询延迟 | 一次性成本 | 对改写的效果 | 什么时候选 |
|---|---|---|---|---|---|---|
| **LLM 查询扩写**（复用现有模型） | 无 | 只有当前 query（已在发） | +300–800 ms | ¥0.0003/次 | 中 | 想零新增依赖、能接受多一次调用 |
| **本地 ONNX embedding**（`fastembed` + BGE-small-zh） | **~100 MB**（不装 torch） | 否 | 10–20 ms | 磁盘 100MB | 高 | 真实聊天记录要进来 |
| **托管 embedding API** | 无（HTTP） | **整段历史**出境（建索引时） | 30–80 ms | ¥0.2/万条 | 高 | 只有合成数据、想省事 |

> 注意一个容易被忽略的点：托管 embedding 在**建索引**时要把**全量历史**发出去，
> 比"query 出境"敏感得多。所以隐私排序是：本地 ONNX > LLM 扩写 > 托管 embedding。

**为什么推荐 `fastembed` 而不是 `sentence-transformers`**：后者会拉 `torch`（安装后 1–2 GB），
对一个 20 条样例的学习项目来说太重；`fastembed` 走 `onnxruntime`，模型 ~100MB，CPU 上够用。
这也符合"不下载大模型"的既定原则——100MB 是"模型文件"，不是"跑 7B"。

### 3.4 推荐路线（分三步，每步都先量再走）

```text
Step 0（必做，半天）：扩基准到 30 改写 + 500 条语料 + 15 负样本
  └─ 记录基线：lexical / +扩写 / hashing 三档的 hit@1、hit@3、MRR、误报率

Step 1（零依赖，半天）：LLM 查询扩写
  └─ 让模型把"电影票别忘了啊"扩成"电影票 电影 周末 别忘了"
  └─ 达标线：hard 组 hit@1 提升 ≥ 0.2，且误报率不升
  └─ 不达标就进 Step 2

Step 2（按隐私选）：
  ├─ 只用合成数据 → 托管 embedding（最省事）
  └─ 真实记录要进来 → fastembed 本地 ONNX + 阈值重标定
```

**阈值必须按后端重标定**：现在的 `MIN_EVIDENCE_SCORE=0.12` 是为 bigram 量身定的，
换 embedding 后分数分布完全不同，直接用会全军覆没或全放行。规则：
用 30 条标注 query 跑一遍，取"噪声上沿 + 余量"作为新阈值（和当初定 0.12 的方法一致）。

### 3.5 验收指标与门禁

| 指标 | 门槛 | 说明 |
|---|---|---|
| hard 组 hit@1 | ≥ 0.6 | 从 0 提到 0.6 才算"解决了改写" |
| 全组 hit@3 | ≥ 0.9 | 检索给 top-3，命中即可 |
| no_match 误报率 | ≤ 0.1 | 不能为了召回而乱召回 |
| 查询延迟增量 | ≤ 100 ms | 超过就别要 |
| 改写后回复是否引用证据 | 100% | 抽出 10 条人工看，回复必须能对上召回句 |

### 3.6 风险

| 风险 | 缓解 |
|---|---|
| 扩基准时"照着实现写 query"（过拟合） | 先写 query 再跑，跑完不改 query 只改实现；留 1/3 做留出集 |
| 合成语料不像真人说话 | 明确写进文档：合成语料只测"排序能力"，不测"语言分布" |
| 本地模型首次下载失败 | 作为可选依赖，缺失时自动退回词法（现有 `build_retrievers` 已是这个结构） |

## 4. 合并执行计划

| 阶段 | 内容 | 需要谁 | 工时 | 产出 |
|---|---|---|---|---|
| **P0** | 埋点（`bench/model_probe.py`：token/TTFT/整轮）+ `--provider`/`--temperature` 对比 + 扩检索基准 | 我，无需 key | 1 天 | 能出"成本/延迟/召回"三张表 |
| **P1** | 真模型验证协议 6 步 | 你的 key | 1 小时 | ✅ **已完成**，见 [`real-model-report.md`](real-model-report.md) |
| **P2** | 按 P1/P0 结果选检索路线（扩写 or ONNX） | 我 | 0.5–1 天 | hard 组 hit@1 数字 + 重标定阈值 |
| **P3** | 人工盲测 10 轮（可选） | 你（3 人标注意愿） | 1 小时 | kappa + 盲测准确率，写进 README |

**P1 实测结论（已回填）**：连通 ✅、整轮 863ms、282 tokens/轮 ≈ ¥0.0003/轮；
规则分 0.4717 < 模板 0.4962（**指标偏置**），语义判定反转（模板 16.7% 幻觉 vs 真模型 0%）；
流式收益仅 13%（回复太短）。详见 `docs/real-model-report.md`。

**P0 的好处**：它不依赖你的 key，也不依赖 `EMBEDDING_*`，做完之后
"要不要上向量库""真模型值不值"这两个问题就从"感觉"变成"看表"。

## 5. 不做的事

| 不做 | 理由 |
|---|---|
| 本地跑 7B 模型（Ollama） | 4–8GB 权重，为了验证链路不值得（已确认放弃） |
| 自研 embedding / 微调 | 30 条基准上无法验证收益 |
| 多向量库并存（Qdrant + Chroma） | 没有第二个场景 |
| 把 `style_similarity` 当"像不像"的最终结论 | 它是规则代理指标，最终结论要靠人工盲测 |
| 在 10 条语料上做任何"检索优化" | 度量不出来 |

## 6. 需要你拍板的三个问题

1. **用哪家的 key**？DeepSeek（直接、便宜）/ 硅基流动或 OpenRouter（有免费额度，先零成本验证）/ 阿里百炼（国内稳）。
2. **语义检索允许下载 ~100MB 的 ONNX 模型吗**（不装 torch）？允许 → 可以走本地路线，隐私最好；不允许 → 只能 LLM 扩写或托管 embedding。
3. **真实聊天记录会不会进来**？会 → embedder 必须本地，且要先做 checkpoint 脱敏；不会 → 托管 embedding 最省事。

这三个问题的答案决定 P2 的走法；P0 无论如何都该先做。
